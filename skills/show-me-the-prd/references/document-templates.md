# 문서 템플릿 -- 4종 디자인 문서 구조

이 문서들은 사람이 읽고 합의하는 동시에, 코딩 에이전트와 goaljaby(PRD → /goal 변환)가 그대로 받아 **만들고, 끝났는지 스스로 판단**하는 데 쓴다. 그래서 모든 요구는 ID로 가리킬 수 있고, 모든 완료 판정은 명령이나 관찰 가능한 결과로 확인할 수 있어야 한다.

## 공통 규칙

- **파일 수**: 기본은 4종 + README = 5 파일. 사용자가 매번 같은 모양을 받아야 예측할 수 있기 때문이다. 4종이 어떤 4종인지는 도메인을 보고 정한다 — `references/domain-doc-sets.md`. 작은 계획은 아래 "짧은 경로"의 한 장 PRD + README 2 파일로 끝낸다.
- **체크박스(`- [ ]`)는 인수 기준과 성공 기준에만 쓴다.** 01_PRD의 기능별 `AC-xx.y` 줄과 `## 5. 성공 기준`이 그 자리다. goaljaby가 체크박스 줄을 완료 기준으로 세므로, 미결 질문·Phase 기능 목록·규칙 목록 같은 다른 목록에 체크박스를 쓰면 완료 기준이 부풀어 오른다. 그런 목록은 일반 불릿(`- `)으로 쓴다.
- **ID 체계**: 기능 `F-01`, `F-02`… / 인수 기준 `AC-01.1`(F-01의 첫째 기준) / 가정 `A-01` / 미결 질문 `Q-01`. 다른 문서는 내용을 다시 쓰지 말고 ID로 가리킨다 — 같은 요구가 두 군데 다르게 적히는 것을 막기 위해서다.
- **미결 사항은 한 곳에만**: 정하지 못한 것은 `01_PRD.md`의 `## 가정 원장`과 `## 미결 질문`에만 적는다. 다른 문서에는 해당 위치에 `> ⚠️ 가정 A-03: {내용} — 아니라면 알려주세요` 인용 한 줄과 링크만 둔다.
- **버전 번호는 기억으로 쓰지 않는다.** 모델이 아는 버전은 낡았을 수 있다. 버전은 문서를 쓰는 시점에 패키지 레지스트리나 공식 문서에서 확인한 값을 적고, 확인하지 못했으면 "작성 시점 최신 안정판 — 착수 시 확인"으로 둔다.

## 짧은 경로 (한 장 PRD)

다음 중 하나면 4종 대신 **한 장 PRD**(`PRD/01_PRD.md`) + `PRD/README.md`만 쓴다. 작은 일에 문서 다섯 장을 만들면 읽는 사람도 에이전트도 핵심을 놓친다.

- 기능이 3개 이하이고 새로 설계할 데이터 구조가 거의 없다
- 버그 수정 하나, 또는 스크립트·CLI 같은 작은 도구 하나다

판정 결과는 가정 원장에 한 줄로 남긴다(예: `A-01 기능 2개라 짧은 경로로 작성 — 4종이 필요하면 알려주세요`). 계획이 커지면 한 장 PRD를 01_PRD로 키우고 나머지 3종을 추가하면 된다.

## 출력 구조 (기본 set — 도메인 미특정 / 모호 시)

```
PRD/
├── 01_PRD.md              # 무엇을, 누구를 위해, 어떤 기준으로 완료인지
├── 02_DATA_MODEL.md       # 데이터 모델 (개념적 ERD)
├── 03_PHASES.md           # Phase별 범위·종료 조건, 사람이 해야 할 일
├── 04_PROJECT_SPEC.md     # 스택, 검증 명령, 완료 정의, AI 작업 규칙
└── README.md              # 네비게이션
```

> 도메인이 명확하면 `references/domain-doc-sets.md`의 절차로 02·03 슬롯 이름을 바꾼다. 01_PRD와 04_PROJECT_SPEC의 구조, 그리고 위 공통 규칙은 어떤 세트에서도 유지한다.

## 문서 1: PRD (01_PRD.md)

```markdown
# {프로젝트명} -- PRD

> 생성일: {날짜} · 생성 도구: Show Me The PRD

## 1. 제품 개요

- **한 줄 요약**: {무엇이고 왜 만드는지 한 문장}
- **해결하는 문제**: {지금 어떻게 하고 있고, 그 방식이 왜 막히는지}
- **핵심 가치**: {기존 대안과 다른 점}

## 2. 사용자

- **누구**: {구체적 대상}
- **상황**: {언제, 어디서 쓰는지}
- **목표**: {이걸로 무엇을 끝내고 싶은지}

### 사용자 시나리오
1. {사용자}가 {상황}에서 {제품}을 열고
2. {행동}을 하면
3. {결과}가 된다

## 3. 핵심 기능

| ID | 기능 | 우선순위 | 복잡도 |
|----|------|----------|--------|
| F-01 | {기능1} | P1 (MVP) | 간단 |
| F-02 | {기능2} | P1 (MVP) | 보통 |
| F-03 | {기능3} | P2 | 복잡 |

### F-01 {기능1}
{무엇을 하는 기능인지 1~2문장}

- [ ] AC-01.1 Given {주어진 상황}, When {사용자가 할 때}, Then {그러면 관찰되는 결과}
- [ ] AC-01.2 Given {주어진 상황}, When {할 때}, Then {결과}

### F-02 {기능2}
{설명}

- [ ] AC-02.1 Given {상황}, When {행동}, Then {결과}
- [ ] AC-02.2 Given {상황}, When {행동}, Then {결과}
- [ ] AC-02.3 Given {실패 상황, 예: 입력이 비었을 때}, When {행동}, Then {오류 표시}

(F-03 이하 같은 형식. 어느 Phase에서 증명할지는 03_PHASES가 정한다.)

## 4. 사용자 흐름

```
{시작} -> {단계1} -> {단계2} -> {완료}
```

1. **{단계1}**: {설명} (F-01)
2. **{단계2}**: {설명} (F-02)

## 5. 성공 기준

- [ ] {제품 수준의 측정 가능한 기준 — 예: 처음 온 사용자가 안내 없이 3분 안에 첫 {핵심 결과}를 만든다}
- [ ] {기준 2}

출시 후에만 잴 수 있는 지표(재방문율 등)는 체크박스 없이 아래에 둔다 — 개발 중에 확인할 수 없는 기준이 완료 조건으로 세어지지 않게.
- 출시 후 지표: {지표와 목표치}

## 6. 안 만드는 것

- {안 만드는 것 1} — 이유: {왜 빼는지}
- {안 만드는 것 2} — 이유: {왜 빼는지}

## 7. 화면과 상태 (UI가 있을 때만)

| 화면 | 관련 기능 | 비었을 때 | 로딩 중 | 오류 | 권한 없음 |
|------|----------|----------|---------|------|----------|
| {화면1} | F-01 | {표시 내용} | {표시 내용} | {표시 내용} | {표시 내용 또는 해당 없음} |

## 8. 오류·예외

- {상황, 예: 외부 API 응답 없음} → {제품이 하는 일, 예: 재시도 1회 후 안내 문구}
- {상황} → {동작}

## 9. 비기능·보안

- **권한**: {누가 무엇을 보고 바꿀 수 있는지}
- **개인정보**: {수집하는 개인정보와 보관·삭제 방식, 없으면 "수집 안 함"}
- **비용 상한**: {월 예상 비용 상한과 넘을 때 동작 — 예: 무료 한도 안, 유료 API 호출은 일 N회로 제한}
- **성능**: {필요할 때만, 숫자로}

## 디자인 방향 (UI 레퍼런스를 수집했을 때만)

{스타일 키워드, 레퍼런스 파일 경로/출처, 각 이미지에서 참고할 점 한 줄. 레퍼런스는 방향 합의용이며 산출물에 재게시하지 않는다.}

## 가정 원장

사용자가 직접 정하지 않아 기본값으로 채운 것. blocking은 틀리면 구조가 바뀌는 가정이라 구현 전에 확인해야 하고, non-blocking은 기본값으로 진행하고 나중에 고쳐도 되는 가정이다.

| # | 가정 | 등급 | 근거 | 영향 문서 | 확인 방법 | 상태 |
|---|------|------|------|----------|----------|------|
| A-01 | {가정 내용} | blocking | {리서치/관행/추론 근거} | 02, 03 | {Turn 4 카드 / 사용자에게 질문 / 문서 확인} | 미확인 |
| A-02 | {가정 내용} | non-blocking | {근거} | 04 | {확인 방법} | 확인됨 |

## 미결 질문

가정으로도 채울 수 없어 사람이 답해야 하는 것. blocking 질문이 남아 있으면 에이전트는 관련 기능에 착수하지 않고 그 질문을 사람에게 넘긴다.

- Q-01 [blocking] {질문} — 영향: F-02
- Q-02 [non-blocking] {질문} — 영향: {범위}
```

### 인수 기준 쓰는 법

- 기능마다 2~4개. 정상 흐름 하나와 가장 흔한 실패 하나는 꼭 넣는다.
- **Then은 에이전트가 직접 확인할 수 있는 결과**로 쓴다: 화면에 보이는 문구, HTTP 상태 코드, 생성된 파일, DB에 생긴 행, 명령 출력. "잘 동작한다", "빠르다", "편하다"처럼 판정할 수 없는 말은 숫자나 관찰 가능한 결과로 바꾼다.
- Given/When/Then 영문 키워드는 그대로 둔다. 사람에게는 "주어진 상황 / 할 때 / 그러면"으로 읽히고, 에이전트와 테스트 도구는 키워드로 구조를 알아본다.

```markdown
## Phase 1: MVP

종료 조건: `{검증 명령, 예: 04_PROJECT_SPEC.md "검증 명령" 표의 전체 명령}`이 모두 기대 결과를 내고, AC-01.1 · AC-01.2 · AC-02.1 · AC-02.2 · AC-02.3을 {e2e 테스트 / 명령 출력 / 스크린샷} 증거로 시연했다.

**전제**: Phase 1 종료 조건 통과

## 사람이 해야 할 일

에이전트가 할 수 없거나 해서는 안 되는 일. 이 항목이 끝나지 않아 막히면 에이전트는 우회(가짜 키, 결제 생략)하지 않고 해당 작업을 "사람 대기"로 표시한 뒤 나머지를 진행한다.
```

## 문서 4: 프로젝트 스펙 (04_PROJECT_SPEC.md)

```markdown
# {프로젝트명} -- 프로젝트 스펙

> 코딩 에이전트가 작업할 때 따르는 규칙과, 완료를 판정하는 방법.

## 기술 스택

| 영역 | 선택 | 버전 | 이유 |
|------|------|------|------|
| {언어/프레임워크} | {선택} | {작성 시점에 레지스트리·공식 문서에서 확인한 안정판} | {리서치 근거} |
| {DB/백엔드} | {선택} | {확인한 버전 또는 관리형 서비스면 "해당 없음"} | {근거} |
| {배포} | {선택} | — | {근거} |
| {인증} | {선택} | {확인한 버전} | {근거} |

버전을 확인하지 못한 줄은 "착수 시 레지스트리에서 최신 안정판 확인"으로 두고, 에이전트는 설치 후 실제 버전을 이 표에 적는다.

## 프로젝트 구조

선택한 스택의 공식 스캐폴드 명령(`{예: 프레임워크의 create 명령}`)이 만드는 구조를 따른다. 아래에는 그 위에 더하는 폴더와 역할만 적는다.

```
{프로젝트명}/
├── {스택 관례의 소스 폴더}/     # {역할}
├── {테스트 폴더}/               # 단위·e2e 테스트
├── {환경변수 예시 파일}         # 키 이름만, 값 없음
└── {의존성 매니페스트}
```

에이전트는 이 표로 작업이 맞는지 확인한다. 해당 없는 단계는 "해당 없음 — {이유}"로 적는다.

| 단계 | 명령 | 기대 결과 |
|------|------|----------|
| lint | `{명령}` | 오류 0개, 종료코드 0 |
| typecheck | `{명령}` | 오류 0개 |
| test | `{명령}` | 전부 통과, 실패 0 |
| e2e | `{명령}` | 현재 Phase의 AC 시나리오 전부 통과 |
| build | `{명령}` | 산출물 생성, 종료코드 0 |

## 완료 정의

아래가 모두 참일 때만 "완료"라고 말한다.

- 검증 명령 표의 모든 명령이 기대 결과를 낸다
- 현재 Phase의 인수 기준(03_PHASES.md)이 테스트나 실행 증거로 시연됐다
- 가정 원장에 확인 안 된 blocking 가정이 없고, blocking 미결 질문이 없다 (남아 있으면 그 기능은 미완료로 보고한다)
- 비밀값이 저장소에 커밋되지 않았다
```

## 문서 품질 체크리스트

문서를 쓴 뒤 스스로 확인한다. 하나라도 어긋나면 고치고 납품한다.

- 모든 기능에 `F-xx` ID와 2~4개의 `AC-xx.y` 체크박스가 있고, 각 Then이 관찰 가능한 결과인가
- 체크박스가 인수 기준과 성공 기준 밖에 쓰이지 않았는가
- 모든 P1 인수 기준이 03_PHASES의 Phase 1에 배정됐고, 모든 Phase에 명령이 포함된 `종료 조건:`이 있는가
- 04_PROJECT_SPEC의 검증 명령이 단계마다 기대 결과를 갖고 있는가
- 기술 스택 버전이 기억이 아니라 작성 시점 확인 값이거나 "착수 시 확인"으로 표시됐는가
- 미결 사항이 01_PRD의 가정 원장·미결 질문에만 있고 다른 문서에는 링크만 있는가
- "안 만드는 것"이 비어 있지 않고, 모든 기술 선택에 이유가 있는가
