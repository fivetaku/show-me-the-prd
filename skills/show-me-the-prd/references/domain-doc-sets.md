# Domain Doc Sets — 4종 문서 동적 생성 가이드

> 사용자는 항상 4종 + README를 받는다(짧은 경로는 예외 — `document-templates.md`). 매번 같은 모양이어야 예측할 수 있기 때문이다.
> 4종이 어떤 4종인지는 도메인을 보고 정한다. 이 문서는 고르는 메뉴가 아니라 **정하는 절차 + 참고 예시**다.

---

## 핵심 원칙

1. **4종 + README = 5 파일** (작은 계획은 짧은 경로의 한 장 PRD + README)
2. **4 차원이 모두 채워져야 한다**:
   - **요구사항** — 무엇을 만들지 (항상 `01_PRD.md`)
   - **구조** — 데이터/모델/시스템
   - **도메인 특화** — 이 도메인의 특수 사항: 규제/흐름/단계
   - **AI 행동 규칙** — 검증 명령·완료 정의·작업 규칙 (항상 `04_PROJECT_SPEC.md`)
3. **01_PRD와 04_PROJECT_SPEC의 구조는 바꾸지 않는다.** 기능 ID·인수 기준·가정 원장(01)과 검증 명령·완료 정의(04)는 에이전트와 goaljaby가 완료를 판정하는 근거라서, 도메인이 달라도 같은 자리에 있어야 한다.
4. **Phase와 종료 조건은 어느 세트에나 있어야 한다.** 03 슬롯이 PHASES가 아니면(예: COMPLIANCE), 그 문서 끝에 `## Phase와 종료 조건`(Phase별 포함 AC ID, `종료 조건:` 줄)과 `## 사람이 해야 할 일`을 붙인다.

예시를 메뉴처럼 쓰면("B2B SaaS면 이 4종") 사용자 아이디어의 세부가 무시된다. 예시는 슬롯이 도메인 이름으로 바뀌는 방식을 보는 용도다.

---

## 동적 생성 절차

Turn 1~2 답변과 리서치로 도메인을 추정한 뒤, Turn 3 초안 작성 직전에 정한다.

### 1. 도메인 핵심 추출
- 누가 쓰는 제품? (사용자 / 머천트 / 의료진 등)
- 핵심 데이터는? (트랜잭션 / 콘텐츠 / 사용자 데이터)
- 도메인 특수 사항은? (결제 / 규제 / 학습 / 의료 등)
- 외부 제약은? (개인정보 규제 / 의료 규제 / 결제 표준 등)

### 2. 4 차원 매핑
| 차원 | 결정 사항 |
|---|---|
| 요구사항 | 항상 01_PRD |
| 구조 | DATA_MODEL / PIPELINE / CURRICULUM 등 — 도메인의 핵심 구조 |
| 도메인 특화 | PHASES / COMPLIANCE / PAYMENT_FLOW / LICENSE_MODEL 등 |
| AI 행동 규칙 | 항상 04_PROJECT_SPEC (도메인 가드는 이 안에 추가) |

### 3. 결정과 기록 — 따로 묻지 않는다

명령의 질문 예산(열린 탐침 + 카드 2콜)에는 문서 세트를 확인하는 단계가 없다. 세트 확인 질문을 추가하면 예산을 넘기고, 사용자는 문서를 보기 전에 판단하기 어렵다. 그래서:

- 위 매핑대로 정하고, 01_PRD.md 가정 원장에 non-blocking 한 줄로 남긴다. 예: `A-02 이커머스로 보고 03을 PAYMENT_FLOW로 구성 — 다른 구성을 원하면 알려주세요`
- 사용자는 Turn 4 확인 카드나 납품 후 잔여 가정 목록에서 바로잡을 수 있다.
- 도메인 추정이 모호하면 예시 0(기본 set)을 쓰고, 그 사실을 원장에 남긴다.

## 참고 예시

> 같은 도메인이라도 세부에 따라 4종이 다르다. "이커머스"도 C2C 마켓플레이스 / 구독 박스 / 라이브커머스면 03 슬롯이 달라질 수 있다.

### 예시 0 — 기본 (도메인 미특정 / 모호)

| # | 파일 | 차원 |
|---|---|---|
| 01 | PRD.md | 요구사항 |
| 02 | DATA_MODEL.md | 구조 (개념적 ERD) |
| 03 | PHASES.md | 도메인 특화 (단계 분리) |
| 04 | PROJECT_SPEC.md | AI 행동 규칙 |

### 예시 1 — B2B SaaS

| # | 파일 | 차원 |
|---|---|---|
| 01 | PRD.md | 요구사항 |
| 02 | DATA_MODEL.md | 구조 (멀티 테넌시 + 권한 모델) |
| 03 | COMPLIANCE.md | 도메인 특화 (개인정보·산업 규제, 테넌트 분리·과금 규칙) + Phase와 종료 조건 |
| 04 | PROJECT_SPEC.md | AI 행동 규칙 + 테넌트 데이터 분리 가드 |

### 예시 2 — 1인 도구 / 사이드 프로젝트

기능이 3개 이하면 먼저 짧은 경로(한 장 PRD)를 검토한다. 그보다 크면:

| # | 파일 | 차원 |
|---|---|---|
| 01 | PRD.md | 요구사항 (짧게) |
| 02 | DATA_MODEL.md | 구조 (저장하는 것만, 가볍게) |
| 03 | MILESTONES.md | 도메인 특화 (작은 단계별 범위·종료 조건) |
| 04 | PROJECT_SPEC.md | AI 행동 규칙 |

## 이 문서를 늘리지 않는다

새 도메인이 오면 이 문서에 예시를 추가하지 말고 그 자리에서 4종을 정한다. 예시가 늘수록 메뉴처럼 쓰이고, 목록에 없는 도메인을 억지로 끼워 맞추게 된다.
